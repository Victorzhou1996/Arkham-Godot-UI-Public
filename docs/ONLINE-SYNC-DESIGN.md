# 联机对局同步设计（EOS 大厅 + P2P）

状态：草案，2026-11-22。已实现的部分标"已做"，没在两台机器上验证的标"未验证"。

## 0. 2026-11-22 晚：已实现的第一版（`app/Scripts/Online/OnlineGame.cs`）

- 房间界面接上了 EOS：建房立刻显示房间码，可复制；有人加入、入座、准备、离开时，界面自动刷新。主持人在所有人入座并准备后才能开始。
- 对局同步：主持人那台跑规则核心，是唯一权威。
  - 其他玩家的牌桌用 `RemoteBackend`：读取局面、提交回答都发请求给主持人，由主持人的核心执行。
  - 主持人收到请求后检查：座位是否属于发请求的人、步数是否是当前步。不符合就拒绝，对方重新读取。
  - 任何一步之后，主持人通知所有人新的步数，各自重新读取局面。
- 消息格式：JSON 信封，gzip 压缩后切成每块 1100 字节，用 EOS P2P 可靠有序发送，接收方拼回。
- 分工（11-22 晚第二版）：新游戏每位玩家在房间里从自己的牌组库选牌组（调查员随牌组），客人的牌组经 P2P 发给主持人，开局 ChooseDeck 时由主持人代为提交；战役设置和章节之间的"继续"由主持人处理（`OnlineGame.HostSteps`）；升级牌组由各自操作（客人升级时向主持人读取存档里的牌组、已用调查员，`side` 请求）。其他步骤谁的座位谁操作；轮到别人时，牌桌顶部显示"等待 … 操作…"。
- 撤回只有主持人能做。
- 手机没有规则核心也能当客人：`Services` 在没有核心时照样加载卡牌、文本和牌组；`App.CoreMissing` 让手机显示自己的菜单。
- 验证情况：
  - 已验证：同一台电脑上开两个游戏，用本地 TCP 连接代替 EOS（`--online-loop=host:端口` / `join:端口`，客人加 `--qa-no-core` 模拟手机）。两个场景都跑通了：①旧存档，客人回答选项、分配恐惧，主持人同步；②新战役，主持人选两套牌组，客人分配创伤、读引言、调度手牌，双方进入第一回合。截图在 `evidence/online/`。
  - 已验证：EOS 房间界面以主持人身份建房、显示房间码（`evidence/online/room-host.png`）。
  - 未验证：通过 EOS 的两台机器实际对局。同一个 Windows 账户下两个游戏是同一个 EOS 身份，本机测不了，要用手机或另一台电脑。
- 已验证（第二版）：本地连接下客人发来自己的牌组（艾格尼丝），主持人开局时用它提交，双方进入第一回合；客人的 `side` 请求成功。房间界面放大、每个座位有底色（`evidence/online/room-demo2.png`、`pickdeck.png`）。
- 未验证：客人在章节之间自己升级的完整流程（需要打完一章）。
- 还没做：断线重连后补发局面（加入房间会补发开局消息，但对局中掉线未专门处理）；两边规则核心版本校验。

## 2. 总体结构

- **大厅（Lobby）只管房间**：房间码、游戏 ID、标题、人数上限、每位成员的名字、准备状态、座位、调查员代码。大厅属性的更新会广播给所有成员，所以界面看到的房间状态来自大厅，不靠 P2P。
- **P2P 只管对局消息**：玩家之间直接发消息，不经过服务器。EOS 的中继（relay）负责跨网络的连接。
- **主持人那台机器是唯一权威**：跑规则核心（`Arkham.NativeHost` / `arkham_core`），决定局面。其他玩家不在本地结算别人的座位。

## 3. 对局同步方案

### 3.1 角色

- 主持人：建房的那台，`HostAsync` 时的 `LocalUser`。持有权威的局面。
- 玩家：加入房间的人。每人占一个座位（`SEAT` 成员属性）。

### 3.2 一次回答的流程

1. 轮到某个座位回答（例如调查员 2 选择行动）时，主持人把"等待座位 2 回答"的问题发给所有人（广播一条 `Prompt` 消息）。
2. 座位 2 的玩家在界面上选择，本机只发一条 `Answer { seat = 2, answer, stateVersion }` 给主持人。
3. 主持人收到后检查：
   - 发送者是否真的占着座位 2（用 P2P 的对端 PUID 和大厅里的座位属性对照）；
   - `stateVersion` 是否等于当前版本，过期的回答直接丢弃；
   - 规则核心是否接受这个回答（`S.Backend.Open(gameId, seat)` / `Answer`，核心本来就按座位校验）。
4. 通过后主持人推进局面，版本号加一，把新状态广播给所有人（`StateUpdate { version, ... }`）。
5. 不通过的回答，主持人只回复 `Rejected { reason }` 给发送者。

玩家不发送"我的局面"，只发"我的回答"。这样任何一方都不能伪造别人的座位行动。

### 3.3 消息格式

- 信封：`[version: 1 字节][kind: 1 字节][payload]`。当前 `EosP2P.Version = 1`。接收方丢弃版本号不认识的消息，所以新版不会误读旧消息。
- EOS 一个包最多 1170 字节，`EosP2P.MaxPacket` 已限制。局面快照可能超过这个长度，需要分片（未做）或只发增量。
- 消息类型（草案）：`Hello`（名字、版本、规则核心的 sourceId）、`Prompt`、`Answer`、`Rejected`、`StateUpdate`、`Snapshot`（断线重连用，分片）、`Leave`。

### 3.4 版本一致性（重要）

Windows 发布版的规则核心 sourceId 是 `5bb054d7…`，当前仓库源码生成的是 `6d0e945d…`，Mac 构建会得到 `6d0e945d…`。**两台机器的规则核心不同，就不能保证同一局的结算一致。**

所以 `Hello` 里必须带 sourceId，主持人和玩家发现不一致时直接拒绝加入，并给出一句中文原因。跨平台联机之前，还要用同一批存档在两台机器上跑结算，对比结果（未做）。

### 3.5 断线与离开

- 主持人离开：房间结束（`DisableHostMigration = true`）。这是第一版的选择，主持迁移需要另行设计（未做）。
- 玩家离开：大厅成员状态变为 Left 或 Disconnected，主持人把该座位释放并广播。
- 玩家重连：未做。第一版不支持中途重连。

## 4. 跨平台（Win ↔ Mac）

- 代码不写死平台：`EosOnlineService` 和 `ArkhamApp.csproj` 都用条件编译（`EOS_PLATFORM_WINDOWS_64` / `EOS_PLATFORM_OSX`）。
- 原生库：Windows 是 `EOSSDK-Win64-Shipping.dll`，Mac 是 `libEOSSDK-Mac-Shipping.dylib`。两者都由 `ArkhamApp.csproj` 复制到输出目录。
- Mac 的 SDK 路径要用绝对路径传入：`-p:EosSdkDir=/Users/<你>/.arkham/eos-sdk-1.19.2.1`（MSBuild 不展开 `~`）。
- Mac 版的原生库加载走 `ResolveNative`（同一个解析器，按程序集目录找 `.dylib`）；**Mac 上尚未验证。**

## 5. 需要 Yunke 决定的事

1. **客户端密钥（Client Secret）怎么放进发布包。** 开发期从 `~/.arkham/eos-config.local.json` 读取。如果随游戏包发出去，密钥就等于公开。这个决定之前不打包。
2. **房间标题从哪来。** 目前 `HostAsync(gameId, seats)` 没有标题参数，大厅标题写死为"联机调查"。如果要显示战役名，需要给接口加一个参数（找界面那边的会话改）。
3. **`OnlineMember` 缺少玩家的 PUID。** 座位归属要靠 PUID 判断，目前成员记录里没有。建议加一个字段 `string UserId`（需要界面那边的会话同步修改）。
4. **是否允许中途重连**（第一版不支持）。
