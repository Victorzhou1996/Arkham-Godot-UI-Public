# 牌组工坊接入 arkham.build · 计划（2026-11-18，待 Yunke 定方案）

## 一、现状（我查到的事实）

1. **现在的工坊后端不是 build**：`WorkshopScreen` 调的是规则核心 DLL 自带的 `deckBuildSchema` / `deckBuildValidate`（`engine/PrototypeBackend.cs`）。它能判断"这副牌能不能开局"，但没有 build 那些功能：牌池筛选、BuildQL 搜索、侧牌组、可定制卡、禁卡表、升级记录、统计等。
2. **build 是什么**：arkham.build 是开源的网页组牌器（`github.com/arkham-build/arkham.build`，TypeScript，React 前端 + Hono 后端，许可证 **AGPL-3.0**）。组牌规则写在它的前端代码里：调查员牌组选项、可用范围、限制、专属卡、升级经验、可定制卡等，都在浏览器里算。
3. **本机已经有一份完整的 build**：0712 的绿色版 `green-packages/green-1.0.39-fast-20261118/` 里有：
   - `dist/build/`：build 网页本体，27 MB，已汉化；
   - `dist/build-api/v1/cache/`：卡牌和元数据缓存（en / zh / zh-cn），22 MB，可以离线使用；
   - `godot_wry.dll` + `WebView2Loader.dll`：Godot 的网页视图插件。绿色版就是用它把 build 嵌进 Godot 外壳的。
   
   也就是说，html 版本当时就是"Godot 外壳 + 网页 build"。你给的网址 `<OVERSEAS_SERVER_HOST>/build/` 是同一份 build 部署在服务器上。

## 二、三种接法

| 方案 | 做法 | 组牌规则 | 界面 | 主要风险 |
|---|---|---|---|---|
| **A 直接嵌网页** | 用 godot_wry 在工坊里打开本地的 `dist/build`，再注入我们的 CSS | 和 build 完全一样 | 只能改颜色、圆角这类样式，布局还是网页的，做不成炉石那种界面 | 牌组存在网页的浏览器存储里，要搭桥同步到游戏；网页视图和 Godot 画面不好融合 |
| **B 原生界面 + build 规则引擎（推荐）** | 把 build 里纯规则的那部分代码（读卡、可用范围、校验、升级经验）单独打包成一个 JS 文件，在 C# 里用嵌入式 JS 引擎（Jint，纯 C#，不需要装 Node）运行；界面全部用 Godot 原生重做 | 和 build 一致（运行的就是它的代码） | 完全按我们的风格和炉石布局 | 要从 build 源码里把规则代码挑出来单独打包，第一次工作量最大；build 更新后要重新打包 |
| C 隐藏网页当规则引擎 | 原生界面，后台开一个看不见的 build 网页，通过 JS 调用它内部的数据 | 一致 | 原生 | 依赖压缩过的网页内部结构，build 一更新就可能坏，不推荐 |

**我建议走 B**。规则和 build 一致，界面完全由我们做，也不依赖网页视图。另外，规则核心的 `deckBuildValidate` 保留，作为开局前的最后一道检查：build 说合法、但核心不支持的情况（比如核心还没实现的卡），在开局前拦下来。

**许可证要注意**：build 是 AGPL-3.0。B 方案直接运行它的代码，只是自己用没有问题；如果以后要对外发布游戏，整个程序需要按 AGPL 开源。这一点需要你知道并确认。

## 三、界面分成三页

### 1. 牌组库（进入工坊的第一页，对应你的截图 3）
- 左侧是牌组列表，每个牌组一张卡片：
  - 调查员头像小卡；
  - 牌组名、调查员名、经验值、"张数（含专属）"，例如 30 (35)；
  - 指针移上去，卡片底部出现一排图标：编辑、升级、复制、导出、**删除**。删除前弹窗确认，删掉的牌组先移到"最近删除"，不会立刻消失。
- 列表上方：**创建卡组**、搜索框、按调查员 / 职业筛选、排序（最近更新、名称、调查员）。
- 右侧是选中牌组的预览：调查员插画、按类型分组的卡表、经验和张数，以及"编辑这副牌""用它开局"两个按钮。
- 导入：粘贴 ArkhamDB 或 build 的牌组链接、JSON。按 build 的格式读入（以后再做）。

### 2. 创建卡组（点"创建卡组"才进入）
- 第一步选调查员：按大盒分组，用头像小卡排成网格。目前能玩的是基础和敦威治，其余大盒灰显，写"暂未支持"。
- 第二步填牌组设置（字段全部取自 build）：牌组名、正反面（平行调查员）、专属卡的选择、调查员的牌组选项（比如有些调查员要选一个职业）、禁卡表。点"创建"进入编辑器。

### 3. 编辑器（就是现在的炉石布局，只换数据来源）
- **左边卡册**：卡池、可选范围、灰显原因都来自 build 的"可用范围"计算。
  - 下方：费用宝石、查找框。查找框支持 build 的 BuildQL 写法，例如"特性:法术 费用<3"。
  - 上方：职业、类型、等级、特性、槽位、"仅可用卡"。
- **右边牌组**分页签：主牌组 / 侧牌组 / 额外牌组 / 附属卡。
  - 每一行和现在一样，可以点、拖、悬停看大图。
  - 列表下方是 build 的校验结果，逐条写成中文：缺几张、哪张超限、哪张不能用、经验超了多少。
  - 底部：张数、经验、保存。
- 统计页签：费用曲线、技能图标数、职业分布（对应 build 的 Deck stats）。
- 可定制卡：在卡上打勾选择升级项（build 的 customizable）。
- **战役升级模式**：经验花费、升级历史，计算方式和 build 的升级逻辑一致。

### build 元素放在哪里

| build 里的元素 | 我们放在哪里 |
|---|---|
| 牌组列表 / 收藏 | 第 1 页左侧 |
| 选择调查员（按大盒分组） | 第 2 页第一步 |
| 牌组设置（名称、禁卡表、正反面、选项） | 第 2 页第二步；编辑器右上角也能再改 |
| 筛选条件侧栏（职业、类型、等级、费用、特性、属性、槽位…） | 卡册上方一行常用项，其余放进"更多筛选"抽屉，从右侧滑出 |
| BuildQL 搜索 | 卡册下方查找框 |
| 卡牌列表（分组：调查员 / 支援·手 / …） | 卡册按页显示；分组变成翻页时的小标题 |
| 牌组面板（主 / 侧 / 附属） | 右侧页签 |
| 校验信息 | 右侧列表下方，中文 |
| 统计 | 右侧"统计"页签 |
| 升级 / 历史 | 战役升级模式下右侧多出"本次升级"页签 |

## 四、分几步做

1. **规则引擎打包（B 方案的核心）**
   - 从 build 源码里把"读卡数据 → 牌组解析 → 可用范围 → 校验 → 升级经验"这条链单独打包成一个 JS 文件；
   - C# 里用 Jint 运行它，读本地的卡牌缓存（直接用绿色版带的 `build-api/v1/cache` 中文数据）；
   - 拿现有的 10 位调查员示例牌组逐一对照：build 网页给出的结论，必须和我们引擎给出的一致。
2. **牌组库页 + 删除 / 复制 / 导出**：牌组存储沿用现在的 `decks.json`，格式对齐 build 和 ArkhamDB 的牌组 JSON。
3. **创建页**：选调查员、牌组设置。
4. **编辑器换数据源**：卡册和校验改用 build 引擎；补上侧牌组、附属卡、统计、可定制卡。
5. **战役升级模式**接入 build 的升级逻辑，替换现在 `WorkshopUpgrade.cs` 里自己写的经验算法。
6. **开局前**仍用规则核心做最终校验，两边结论不一致时写进日志，方便查。

## 五、需要你决定的

1. 走 B 方案（原生界面 + build 规则引擎）吗？还是先用 A（直接嵌网页）快速拿到完整功能，再慢慢替换？
2. AGPL 许可：确认可以接受吗（目前只自用就没有问题）？
3. 卡池范围：是只开放基础 + 敦威治（现在规则核心能玩的），还是允许组所有大盒的牌、只是开局前拦下？
